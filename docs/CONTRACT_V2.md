# SiteMind v2 contract — live events + any package

Two gaps from the judging rubric, closed in v2:

1. **Challenge 1.3's input is "a stream of events".** Judges must be able to fire events at a
   running job (late reply, price change, date slip, missing document, tool failure, approver
   away, restart) and watch the agent react, instead of only watching a scripted scenario.
2. **Track 01 wants an agent for jobs it was not built for.** SiteMind must run a *second,
   different* package with zero code changes, read the package and fields from the plain-English
   goal, accept an uploaded spec PDF, and hand off to a human when it cannot support a package.

Models live in `backend/sitemind/models.py` (section "v2"): `PackageSpec`, `GoalParseRequest`,
`GoalParseResult`, `SpecUpload`, `EventType`, `EventParamSpec`, `EventTypeSpec`,
`InjectEventRequest`, `InjectedEvent`; plus `CreateRunRequest.package_id/spec_upload_id` and
`RunSnapshot.package_id/events`. Mirror them in `frontend/src/types.ts`. Do not rename fields.

## Live events (owner: core)

API (all JSON, typed with the models above):

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | /api/packages | – | `PackageSpec[]` |
| POST | /api/goal/parse | `GoalParseRequest` | `GoalParseResult` (deterministic parse; LLM may only fill `questions` wording) |
| POST | /api/specs | multipart `file` (PDF ≤ 10 MB) | `SpecUpload` (stored under `$SITEMIND_DATA/uploads/`) |
| GET | /api/event-types | – | `EventTypeSpec[]` (titles, descriptions, params with defaults/ranges) |
| POST | /api/runs/{id}/events | `InjectEventRequest` | `RunSnapshot` (event recorded `pending`) |
| GET | /api/demo/defaults?package_id= | – | `CreateRunRequest` for that package |

Semantics:

- Events go into an `events` table (app DB). The worker drains pending events at the start of
  every `monitor` super-step. Applying an event is idempotent: key `{run}:event:{id}:apply`
  via `perform_once`; status -> `applied` with `applied_sim_time`, a one-sentence `outcome`, and
  the `triggers` it raised. Every application writes an audit entry (actor `human` for the
  injection, the reacting specialist for the reaction) and a timeline event (lane `human`/`system`).
- If the worker is parked at an approval (`waiting_human`) or not alive when an event arrives,
  the API spawns a worker so the event is processed now. If the event invalidates the pending
  approval's memo (e.g. price change on the recommended vendor), the agent supersedes that
  approval (status `rejected`, decided_by `system: superseded by <event id>`), re-plans, and asks
  again with a fresh memo. On a completed run, events are recorded `ignored` with the reason.
- Reactions (must be real logic, then re-plan via the existing trigger machinery):
  - `vendor_late_reply {vendor_id, days}`: that vendor's pending/next reply arrives N sim days
    later; if it pushes past the RFQ deadline -> chase task, then fallback to other vendors.
  - `price_change {vendor_id, pct}`: revised quote (new revision) -> re-level, budget check,
    re-rank; breach -> re-plan + escalate.
  - `date_slip {vendor_id?, days, target}`: `lead_time` -> that vendor's lead time +N d, CPM
    recomputed, float may go negative -> re-plan (expedite/alternate); `required_on_site` ->
    the site date moves (±N), every option re-scheduled.
  - `document_missing {vendor_id, document}`: vendor submittal incomplete -> chase task; the PO
    cannot be released to that vendor until received (or a human waives it at approval).
  - `tool_failure {tool, count}`: the next N calls to that specialist raise; retried with
    backoff (sim time), after max retries -> fallback/escalate, all logged.
  - `approver_unavailable {days}`: approvals wait N sim days; the agent sends a reminder/delegation
    note (logged side effect) instead of acting alone.
  - `restart`: SIGKILL the worker and spawn a new one (same as kill + resume buttons).
- `RunSnapshot.events` lists every injected event with status/outcome.
- Package plumbing: `CreateRunRequest.package_id` selects catalogue, scenario and spec PDF;
  `spec_upload_id` swaps in the uploaded PDF for the takeoff. Task titles and memo/PO text use
  the package title (no hard-coded "switchgear" in generic code paths).

Tests (core): inject each event type into a running run and assert the reaction + re-plan +
no duplicate outbox messages; inject during `waiting_human` and assert supersede + new approval;
a full `dg-2mw` run completes with a PO; goal-parse endpoint; spec upload + takeoff preview.

## Frontend (owner: frontend)

- Goal composer: free-text goal is parsed live (`POST /api/goal/parse`, debounced) into chips —
  package, project, need-by, budget — each with the evidence span on hover, missing fields and
  the agent's questions shown inline; package selector pre-filled from the parse; "Use sample spec"
  or **upload your own spec PDF** (shows the takeoff preview table with page citations and
  warnings). Unsupported package -> clear "SiteMind will hand this to a human" state.
- **Event console** (on the run view, testid `event-console`): pick an event type
  (`GET /api/event-types`), vendor (from the run's quotes/package vendors), params with
  defaults, optional note, "Inject" (testid `inject-event`). Below it the event feed
  (`events[]`, testid `event-feed`) with pending/applied status and the agent's outcome sentence.
  Events also appear on the timeline (human lane, distinct marker).
- Package-agnostic labels everywhere (header shows the run's package title).
- e2e: launch a run, inject `price_change` on the recommended vendor while waiting for approval,
  see the approval superseded and a new memo; launch a `dg-2mw` run and complete it.
