The problem

On a data-centre job, one switchgear package sets the energisation date.

4–6
months lead time

A 480 V switchgear package is manufactured to order. The hall cannot be energised without it.

Weeks
of email and Excel

Procurement for that one package runs across mail threads and a tracker that someone has to keep current.

1
dropped step

A missed date slips energisation. A duplicated email or order costs money and credibility.

What those weeks contain, and where they break
01Takeoff from the specquantity disagrees with drawing
02RFQs to several vendorssent twice after a hand-over
03Chase the ones that go quietfollow-up nobody sends
04Re-check prices before awardrevision nobody re-budgets
05Lead time vs required-on-site datefloat found negative too late
06Two sign-offsapprover on leave
07Issue the purchase orderordered twice, or not at all

Each step is easy. Staying with all of them for weeks, through restarts and hand-overs, is where the job fails.

Who decides what
  • Code builds the graph and does every quantity, price, date and score.
  • The local model words the rationale and the memo. It never produces a number.
  • Specialists are pure functions, so a replay gives identical output.

Durability

Kill the worker at any point. It resumes, and nothing is sent twice.

1 · Checkpoint per task

The plan is saved after every task

LangGraph StateGraph with SqliteSaver. Each step runs exactly one plan task, then persists the plan, the facts and the simulated time.

The worker is its own OS process. The API and the worker share nothing in memory, so a dead worker loses nothing.

Impact · judging criteria

Built against what challenge 1.3 asks for, and what the judges score.

40 %
Accuracy
Does it get the job right on realistic examples?
  • Every quantity, price, date and score comes from deterministic code and is reproduced by the unit tests.
  • A killed and resumed run ends with the same PO as an uninterrupted one.
30 %
Customer value
Would a procurement manager use it tomorrow?
  • It does the chasing, re-checking and escalating a coordinator does by hand.
  • The demo PO goes out 33 days ahead of the order-by date, with a memo a PM can sign.
20 %
Trustworthiness
Sources cited, sensible confidence, nothing made up.
  • Takeoff lines cite page, table and row. Confidence 0.92, with an RFI where the drawing disagrees.
  • The memo lists the risks of its own recommendation. Synthetic data is labelled everywhere.
10 %
Build quality
Easy to run, cost and speed per run, code quality.
  • One command to start. ₹0 per run on a laptop CPU. 5.4 s with the model off.
  • Typed contract, deterministic test suite with kill-and-resume tests, MIT licence.

What's next · credits

The harness is the product. Procurement is the first job on it.

Next
  1. Email and ERP adapters behind the same ledger, passing the idempotency key to the receiving system.
  2. More job types on the same harness: submittal chasing, RFI follow-up, delivery tracking.
  3. Lead-time ranges from vendor history in place of single values.
  4. Takeoff from real drawing sets, with a review screen where a person accepts each line.
  5. Postgres, authentication, approver roles and delegation.
  6. A kill-at-every-step benchmark that asserts zero duplicate actions across the run.
Limits today

Synthetic vendors and prices. Simulated clock. RFQs and POs go to a mock outbox, with no real email or ERP. One package type and one spec format. Single tenant.
